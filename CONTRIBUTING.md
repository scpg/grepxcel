# Contributing to grepxcel

Thanks for your interest in contributing!

## Branch model

| Branch | Purpose |
|---|---|
| `main` | Stable, always green. Never commit directly — changes arrive via PR from `dev`. |
| `dev` | Active development. **All pull requests target this branch.** |

## Step-by-step guide

### 1. Fork the repository

Click **Fork** on the top-right of the GitHub page. GitHub creates your own copy of the repo under your account.

### 2. Clone your fork

```bash
git clone https://github.com/<your-username>/grepxcel.git
cd grepxcel
```

### 3. Set up the development environment

```bash
python -m venv .venv

# Core dependencies + test runner
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt

# Optional: install the draft feature (heavy — compiles C++ code for local LLM)
# .venv/bin/pip install -r requirements-draft.txt
# Or use the hardware-aware installer (detects CUDA/Metal automatically):
# python3 scripts/install_llm_deps.py
```

### 4. Create a feature branch from `dev`

Always branch off `dev`, never off `main`:

```bash
git checkout dev
git pull origin dev          # make sure you're up to date
git checkout -b my-feature
```

### 5. Make your changes

A few rules:

- No inline `python -c "..."` scripts — put any one-off code in `tmp.local/`
- snake_case for variables/functions, CamelCase for classes
- Maximum line length: 88 characters
- All tests must pass before opening a PR

### 6. Run the tests

```bash
.venv/bin/pytest tests/ -q
```

### 7. Push and open a Pull Request

```bash
git push origin my-feature
```

Then open a PR on GitHub. **Set the base branch to `dev`**, not `main`:

```
your-fork:my-feature  →  scpg/grepxcel:dev
```

In the PR description include:

- What the change does and why
- Any test evidence (new test added, or existing test output)

## CI

GitHub Actions runs the full test suite on every push and PR. Your PR must be green before it can be merged.

## Test fixtures

Every fixture in `tests/fixtures/<N>_<name>/` contains the following files:

| File pattern | Purpose | Editable by tooling? |
|---|---|---|
| `<name>_data.xlsx` | Source Excel file the engine extracts from | ✅ (it's the input) |
| `<name>_data-cdr.xlsx` | CDR (Content Disarm and Reconstruct) copy — macros, VBA, and external links stripped by OPSWAT MetaDefender, then reconstructed from safe content. Used to test the security layer. | ✅ |
| `<name>_pattern-from-draft.xlsx` | Auto-generated baseline pattern. "From draft" means a starting-point pattern, not necessarily produced by the LLM drafter: fixtures 01–14 have patterns authored as Python code in `scripts/generate_fixtures.py`; fixtures 15–22 were generated by `grepxcel draft`. **Both formats are always kept in sync** — the `.xlsx` is what the engine uses; the `.csv` is the human-readable/editable twin. | ✅ |
| `<name>_pattern-from-draft.csv` | CSV twin of the above (same content, different format) | ✅ |
| `<name>_pattern-manual.xlsx` | Hand-crafted pattern by the project maintainer. **Never overwrite or regenerate.** | ❌ read-only |

The `docs/pattern-reference.xlsx` is a **committed build artifact** generated by `grepxcel docs -o docs/pattern-reference.xlsx`. Regenerate it after any pattern-format change and include it in your PR.

## API keys and environment

Two `.env` template files are provided:

| File | Use case |
|---|---|
| `.env.example` | Minimal template — covers the three API keys (`ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`, `GITHUB_TOKEN`). Copy to `.env` and fill in your keys. |
| `.env.template` | Extended template for 1Password / Snyk workflows. Includes Snyk org/project IDs. Use this if you run `op run --env-file=.env` or use Snyk in CI. |

Both `.env` and `.env.template` are gitignored — never commit real keys.
